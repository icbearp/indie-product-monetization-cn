# Chrome 插件与本地产品

## 先划清三层职责

| 层 | 要确认的能力 | 不能推断的事项 |
|---|---|---|
| 本地产品 | 真实页面读取、任务处理、存储、备份、权限与账号隔离 | 本地有数据不等于云端已同步 |
| 许可证服务（如需要） | 付款对应权益、设备/账号绑定、有效期、恢复和撤销 | 登录成功或收到回调不等于付款成功 |
| 可选云端能力 | 同步、协作或计算的具体数据流与持续成本 | 商业化不代表必须上传所有本地数据 |

允许纯本地产品销售付费版本；是否增加许可证服务取决于产品模型和防滥用需求，不为收款把整个工具改成 SaaS。具体支付、许可与 Chrome 商店政策需查证当前官方文档，技能自身不内置长期有效的合规结论。

## 插件的首次成功体验

建议按产品实际需要裁剪：安装 → 清楚说明所需站点权限 → 识别当前账号/上下文 → 执行一个真实任务 → 显示结果及覆盖范围 → 保存/重开可用。多个 Chrome 分身分别处理，不能假定共享同一登录、存储或许可证。

网页读取尤其要区分：任务未开始、读取中、部分完成、完成、失败、需要用户操作。显示读取时间、来源、数量、范围和错误原因；无法获得操作时间时，不把发现时间当成操作时间。没有观测到关系不能直接写成未关注、已取关或未回关。

例如只读取当前关注列表的 50 条，只能承诺“已读取部分关注关系”。今天的点赞/回复若无法完整读取，不宣传“自动同步今天所有互动”。失效页面、登录过期和 DOM 变化是产品交付风险，应纳入错误提示和维护成本。

## 收费边界与交付

可以讨论“基础本地任务 + 付费高级分析/批量处理”等方案，但须先验证付费部分的真实价值，不预设此结构永远最佳。数据导出、退款后数据访问和版本支持范围要明确；用户自有数据的备份恢复不应被突然撤销的授权锁死。

若采用在线许可，列出激活、有效、临近到期、过期、退款撤销、无法联网、换设备和恢复状态。明确离线宽限、重试上限与用户提示，不能在网络失败时直接认定未购买，也不能无限重试或默认永久放行。客户端代码和本地布尔值可被修改，授权真实性通常需可信服务验证；不能宣传绝对防破解。

扩展商品页、引导和产品内提示应保持同一套能力描述、数据处理说明、付费范围与支持联系方式。请求最小必要权限，拟上传的数据必须明确；许可证验证与内容数据同步分别说明。

商业化验证记录至少覆盖：干净安装首次任务、重开后数据、错误恢复、账号/分身隔离、真实或支付服务提供的测试交易、重复通知幂等、权益恢复、到期/撤销、备份恢复。只运行模拟测试时明确测试环境；不因此宣称线上支付或商店审核已通过。
